## 실제 네트워크/DB에서 확인한 항목

6개의 서로 다른 게스트 cookie와 6개의 실제 WebSocket 연결을 사용했다. 첫 접속/로비 시작은 정상 초기 세계에서 진행했다. 자원·건설 경합에는 명시적 테스트 fixture를 준비했다. 해당 fixture는 테스트 실행 프로세스에서만 사용하며 운영 HTTP/WS에 자원 생성/순간이동 명령을 추가하지 않았다.

- 6명 입장과 7번째 ROOM_FULL, 각 개인 가방·제작 채널의 full state/StateView 분리.
- 준비 완료와 6인 목표 고정, 서버가 적용한 이동.
- 마지막 자원 1개에 대한 6개 동시 요청: 1명 성공·5명 실패·총량 불변.
- 같은 footprint의 6개 동시 건설: 1개 설비·비용 1회·5개 OCCUPIED.
- 실제 자원 이동 명령을 100회 재전송하고 동일 게스트 새 연결에서 다시 전송: 동일 영수증과 효과 1회.
- 같은 commandId의 quantity 변경 거절, 중복 영수증, 원격 작업 거절.
- 같은 게스트 새 연결의 controller epoch 교체.
- Origin/CSRF 거부, 일반 참여자의 소유자 명령 및 일반 방 코드에 의한 소유권 복구 거부.
- 전원 이탈 후 tick 정지, 스냅샷 저장/로드 hash 일치, 동일 멤버 재접속.
- 두 writer의 동시 lease 거부, 이전 writer epoch COMMIT 거부.
- 최신 스냅샷 손상 → 이전 스냅샷+delta hash 일치. 이어서 delta 하나를 제거하면 SAVE_CORRUPT이며 원래 durable head가 유지됨.

**실행하지 않은 장애 시험:** 실제 process kill 타이밍 주입, COMMIT 응답만 유실하는 프록시, 네트워크 partition 후 lease 만료 조합, 몇 시간 뒤 영수증 재시도, 느린 클라이언트 1MiB 적체, DB 2초 지연 및 3개 방 동시 부하. 구현된 방어 로직이 있다는 이유로 통과 처리하지 않았다.

## 발사까지의 코어 완주

시뮬레이션은 원본 50ms tick 수치를 유지하되 실제 벽시계를 기다리지 않고 논리 tick을 실행했다. 새 방의 빈 가방에서 시작한다. 자원을 직접 넣지 않았고 캐릭터 위치도 직접 대입하지 않았다. 경로를 계산한 뒤 정상 이동 입력으로 이동한다. 필요한 모든 원재료는 채집 또는 유료 수거기를 통해 얻었다.

M1은 수동 제작으로 완료한다. 이후 비용을 실제로 제작·운반·지불해 가공기, 배송 허브, 자동 수거기 3개와 링크 2개를 설치한다. 자동 생산과 실제 비행 cargo가 포함된다. 마지막 세 점검과 전원 동의, 카운트다운, 발사 후 정지도 확인한다.

| 계획 인원 | 마지막 tick | 자동 생산 | 도착 화물 | 소모품/위치 직접 주입 |
|---:|---:|---:|---:|---|
| 1 | 307,164 | 1,880 | 1,786 | 없음 |
| 6 | 755,601 | 3,758 | 3,602 | 없음 |

6인 모형은 생산 요청을 작업자에게 순차 배정하고 조립 시 함께 작업한다. 최소 자동화만 구축한 비효율적 검증 경로이므로 논리 시간 255.97분/629.67분을 사람의 협동 플레이 시간으로 해석할 수 없다. 설계의 목표 플레이시간과 재미·공장 규모 밸런스는 아직 검증하지 않았다. 경제 값을 이 시험에 맞추어 바꾸지 않았다.

**이 두 결과는 실제 1인/6인 온라인 브라우저 완주를 대체하지 않는다.** 사용자가 요청한 그 완주 검수는 남아 있다.

## 재현

`npm run check`, `npm run test:full`로 코어/빌드를 재현한다. 개발 DB에서 `ORBIT_QA=1`로 서버를 시작하면 통합 시험을 실행한다. 실행 중인 게스트와 무관한 테스트 방을 만든다. QA fixture는 완주 기록과 구분되며 운영 모드에서는 실행되지 않는다. 완료 시점과 시험별 값은 JSON에 저장한다. UI 시험은 `/qa.html`(개발 서버 전용) 또는 실제 브라우저로 수행한다.
